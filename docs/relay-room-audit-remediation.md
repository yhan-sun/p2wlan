# Relay 与房间审查修复

基线：`9f710068b204ca6052be3b3810af06db91af675b`。本次修改不改变 Noise/Probe-v2、Direct 加密验证、候选代次、房间 30 秒授权租约或旧队列包的发送许可规则。

## 授权与升级顺序

控制面签发 Relay 票据时，`network_id` 字段代表**转发作用域**，不再一定等于配置文件中的网络 ID。设备和节点 ID 不变，客户端只需携带票据，不需要解码或重写作用域。

个人网络使用 `account-v1:` 加上规范 JSON `[user_id, network_id]` 的 SHA-256；好友房间使用数据库确认的房间 ID，并继续检查成员关系及设备访问权限。旧 Relay 也会按签名后的 `network_id` 隔离新票据，不会把不同账号的个人网络混在 `default` 中。成员跨账号的房间通信保持不变。

**旧票据不会因部署新的控制面自动失效。** 滚动升级期间旧作用域和新作用域之间不能互通，旧票据对应的原有权限窗口也仍然存在。需要受控切换时，应维护窗口内更新 control 与 relay、轮换票据签名 keyring（停止接受旧签名密钥），并让设备重新获取票据及重连。允许滚动升级时，必须明确最长旧票据寿命为 15 分钟，不应宣称部署瞬间完成历史会话隔离。不要修改客户端的真实虚拟网络 ID 来匹配新票据作用域。

`RELAY_REQUIRE_AUTH` 等布尔环境变量使用 Go 严格布尔解析并去除首尾空白。`true`、`TRUE`、`1` 均开启，`false`、`FALSE`、`0` 均关闭；显式空值和非法值使启动失败，不能静默降级。显式启用 legacy 或明文模式仍是独立的开发选项，不建议用于公网部署。

## 中继接入与背压

连接上限已满时直接关闭尚未接入的 socket，不在 accept 循环中触发 TLS 握手以发送应用层错误。已经接入的连接不受该拒绝动作影响。

目标队列满时返回 `4008`，不再关闭目标的整个 Relay 连接。每个目标同时限制队列帧数、4 MiB 在途/排队字节数和单来源占用，并为控制消息预留槽位及 64 KiB 字节空间。这是按来源的准入限制，不是完整的轮询调度器。网络写入有 5 秒期限；仅在目标持续无法消费或本连接控制队列失效时关闭对应连接。`forwarded_frames_total` 仍表示入队，不代表对端解密成功。

## 撤权协议 v2

Relay 使用带专用认证的 `GET /api/v1/relay/revocations?protocol=2&after=N`。响应增加 `protocol_version`、`after`、`next_cursor`、`has_more`，`version` 是独立、持久化、单调递增的高水位。

首次响应有更多页时，后续请求带 `through=version` 固定本轮边界。服务端按序返回最多 256 条记录，并限制每页编码预算为 512 KiB；Relay 继续保留 1 MiB 响应上限。每轮最多读取 64 页；未读完时短间隔继续，不追逐并发写入的无限移动终点。失败只重试未完成页，已经接受的撤权立即生效，完成全部分页后才更新成功同步时间。

初次配置撤权 feed 尚未同步完成时拒绝新的认证注册。连续失联超过 `3 × poll_interval + 10s` 时拒绝新注册，并在轮询检查时关闭已有认证 Relay 连接；因此撤权失联会牺牲 Relay 可用性，而不是默默继续放行。暂时无法同步不会算作客户端密码/票据错误并消耗源地址的认证失败额度。

未配置 feed 的部署保留静态 denylist 与票据到期机制，没有在线撤权同步保障。旧控制面仍可返回 v1 全量快照；超过历史大小限制的旧控制面仍需升级，不能依靠客户端自动绕过响应上限。

服务端和 Relay 内存撤权缓存保留至少 24 小时，远大于票据最长 15 分钟。Relay 验证 `iat/exp` 与最长票据寿命。数据库清理不降低独立高水位，Relay 缓存只在成功同步完成后清理过期条目；静态 denylist 不自动删除。不要复用已删除的 device/credential/JTI 标识，也不要绕过控制面的已撤销凭证检查重新签票。

指标 `/metrics` 增加 `revocation_version`、`revocation_cursor`、`revocation_ready`、`revocation_last_success_unix`。监控应同时检查同步是否就绪、上次成功时间和游标是否持续落后，不能只看失败累计数。feed 重定向不跟随，专用认证不会转发到重定向目标。

## 房间 API 与交互

原样保存 IP 返回 `changed=false, reconnect_required=false`，不撤销凭证、不增长房间 revision、不主动断开信令连接。实际改址保持原有撤权与重连要求。UI 也拦截原样保存，提示“地址未变化，无需重新连接”。

错误码新增 `room_ip_conflict`、`room_device_state_conflict`、`room_invite_limit`，仍保留通用 `room_conflict`。重复审批不再提示 IP 被占用；操作失败后仍刷新名单确认服务端最新状态。

房间列表的定时刷新不因普通 StatusStore/ParallelRooms 通知而重置期限，仅在过渡态/稳定态的轮询间隔真正改变时重排。名单不再被每秒状态通知无限延期。

房间总状态按本机到所有在线 peer 汇总：全部直连、全部中继、直连与中继、部分连通、建立加密会话、直连探测或等待好友。另展示在线、可互通、直连、中继、未连通数量。过期快照显示“状态待更新”，不能当作实时成功。房间在线人数仍是控制面成员统计，不与本机实际可互通设备数混淆。

桌面本地状态与控制面权限同步分别检查。网络超时/GUI 登录过期只产生管理警告，仍读取本地 daemon 和路由；明确收到移出房间、禁止或暂停的决定仍停止对应运行时。daemon 的 30 秒房间授权租约始终有效，GUI 警告不是延长访问权限。手机的单活动网络限制和桌面的并行数量在房间页面分别展示。

## 并行房间端口

桌面首先读取 profile 的 `connection.json` 中可选 `diagnostics_port`；旧文件无字段时仍使用原哈希端口。与主网络或已跟踪房间端口冲突时，在 40000–59999 中最多尝试 32 个备用值，并在启动前持久化选择。恢复运行时使用同一端口，账号切换/停止全部仍保留 epoch 检查。

网段重叠、虚拟网卡标识冲突和无法确认身份的进程仍拒绝操作。此备用机制处理已知本机运行时之间的端口碰撞；系统中的无关进程占用或启动期间的 OS 端口竞争仍由启动门禁安全拒绝，不会强制杀掉其他进程。CLI 重连已有 profile 时保留合法的本地诊断端口，不重新覆盖桌面已分配的端口。

## 验收证据

新增自动回归位于：

- `server/database/relay_audit_test.go`：账号/房间作用域、超过 1 MiB 的历史、多页固定高水位、增量与清理、IP 幂等。
- `server/api/room_audit_test.go`：实际签出票据及身份绑定、HTTP 游标校验、无变化 IP 响应、具体错误码。
- `server/relay/audit_hardening_test.go`：真实 TLS 未握手的容量拒绝、严格布尔配置、背压公平准入/字节预算、分页失败重试、首次同步准入、过期 feed 关闭、重定向拒绝和缓存清理。
- Flutter `room_connectivity_test.dart`、`rooms_page_test.dart`、`room_api_test.dart`、`room_device_controls_test.dart`、`parallel_rooms_test.dart`：汇总、刷新不饥饿、IP 无操作、错误码、控制面与运行时分离、持久化端口和恢复。
- CLI `preserves_desktop_allocated_room_diagnostics_port`：已保存端口不会被覆盖，拒绝公网或越界诊断地址。

现有 Go、Flutter、NAT topology、房间、路径状态机和平台生命周期 CI 门禁保持启用。测试文件的存在不是测试通过证据，实际结果以本 PR 对应提交的日志为准。

以下仍需要真实发布包和多设备验收，不能由上述单元测试代替：持续业务跨多个 Relay 续票周期；双 NAT/双 CGNAT；Wi-Fi 与热点切换；双方同时重连；休眠唤醒；Windows/macOS/Android 的实际 TUN 与路由；多个房间持续流量下的延迟、内存和公平性。验收应记录两端版本、控制/中继版本、时间线、实际业务丢包与最长中断，不能只提供“已直连”截图。
